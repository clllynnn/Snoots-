# Snoots! 一天開發 SCOPE 與分工討論稿

> 時間限制：剩餘不到 1 天
> 文件狀態：團隊 review 版，尚未指派 owner
> 核心原則：先完成一條可以從頭走到尾的 demo，再補支線畫面。

## 1. 這一天只完成一個故事

Demo 主角 Amber 想替慢熟小型犬 Nori 找附近狗友。她在地圖上看到「大安森林公園小型犬慢走團」，打開活動後，Snoots! 根據 Nori、活動參加犬隻與場地條件，顯示「很適合 Nori」及原因。Amber 看完注意事項後報名成功。

完整路徑：

> 地圖首頁 → 活動簡卡 → 活動詳情 → AI 適合度 → 報名成功

這條路徑壞掉，就算其他頁面很好看，這次 demo 仍不算完成。

## 2. 範圍分級

### A. 今天一定要完成（Must）

#### A1. 地圖首頁

- 看得到狗聚、地點、Care 三種類型。
- 至少可以切換三種分類，或用不同標記清楚辨識。
- 點擊主活動標記後，能前往活動詳情。
- 地圖可以是可信的 demo 地圖，不要求一天內完成正式地圖服務。

#### A2. 一場完整活動

- 活動名稱：大安森林公園小型犬慢走團。
- 時間、集合點、活動方式、參加上限、主揪與固定團資訊齊全。
- 顯示至少 3 隻已參加狗狗的基本資料。
- 主要按鈕可以完成「參加」並顯示成功狀態。

#### A3. AI 適合度

- 使用 Nori 的真實 demo 資料、活動條件與場地規則產生建議。
- 結果顯示文字等級與 2 至 3 個具體原因，不顯示百分比。
- 清楚註明這是參考建議，不是安全保證。
- 有 loading 狀態。
- 網路或 AI 失敗時，使用預先準備的 fallback 結果，demo 不能卡住。

#### A4. Demo 資料與視覺一致

- 所有主線畫面使用同一組 Nori、活動、場地與參加犬資料。
- 沿用現有 Snoots! 色彩、字體與卡片規則。
- 重要按鈕至少 44 pt 高，適合 iPhone 操作。

### B. 要出現在 demo，但只做到能說明概念（Show only）

#### B1. 滑卡配對接到活動

- 保留 Mochi 滑卡。
- 配對成功後，顯示「你們都適合這場活動」並可回到同一場慢走團。
- 不做聊天、訊息、封鎖或完整候選人系統。

#### B2. Care 地圖層

- 地圖上至少有 1 至 2 個動物醫院或夜間急診標記。
- 點開後顯示名稱、距離、電話、是否接受夜間急診與最後確認時間。
- 不做症狀判斷與原本多步驟 Care 流程。

#### B3. 地點資訊與付費牆概念

- 至少一張地點詳情顯示基本規則。
- 一小段進階內容呈現 locked 狀態，例如完整個人化分析或規則變動提醒。
- 不串接真實付款、訂閱或帳號權限。

#### B4. 固定團概念

- 活動上顯示「每週三固定舉辦」與本週場次。
- 不做自動建立未來場次、改期、取消與候補。

### C. 保留現況，不再投入（Keep as is）

- Social / Feed 現有畫面。
- 現有狗狗與店家圖片資產。
- 現有滑卡卡片的主要視覺語言。
- 現有 in-memory mock data 架構。

### D. 明確不做（Out of scope）

- AI 拍照生成狗狗檔案。
- AI 破冰開場白。
- 真實登入、後端、資料庫、聊天、推播。
- 真實付款、訂閱、退款與權限管理。
- 正式的固定團管理、臨時揪團即時配對。
- AI 醫療診斷或安全保證。
- 全台店家、正式營運資料與店家後台。

## 3. Demo 所需最小資料

### 狗狗

| 名稱 | Demo 用途 | 最少資料 |
|---|---|---|
| Nori | 使用者自己的狗 | 5 公斤、慢熟、怕大型犬、不喜歡吵雜、適合牽繩散步 |
| Mochi | 滑卡配對對象 | 體型相近、溫和打招呼、接受慢速牽繩介紹 |
| Tofu / Pudding | 活動參加犬 | 簡短體型與個性標籤 |

### 活動

主活動只需要一場，但資料要完整：

- 大安森林公園小型犬慢走團
- 本週六 16:00 至 17:00
- 信義路入口集合
- 每週固定舉辦
- 全程牽繩，上限 8 組，目前 6 組
- 適合小型犬、慢熟犬與第一次參加者

可以再放 1 至 2 場對照活動，讓使用者看得出同一隻狗可能得到不同建議，但不必完成全部報名流程。

### 地點

Demo 建議準備 6 至 8 個集中在大安區、條件差異明確的地點：

- 安靜散步公園
- 小型犬室內聚會空間
- 大型犬或放繩活動空間
- 下雨天備案
- 假日容易擁擠的場地
- 有體型、牽繩或室內外限制的店家
- 1 至 2 個夜間急診或動物醫院

## 4. 畫面清單與完成狀態

| 畫面／狀態 | 優先級 | 完成定義 |
|---|---|---|
| 地圖首頁 | Must | 三種標記可辨識，主活動可點擊 |
| 活動簡卡 | Must | 時間、類型、剩餘名額與「適合 Nori」提示可掃讀 |
| 活動詳情 | Must | 活動、場地、參加犬與主揪資訊完整 |
| AI loading | Must | 使用者知道系統正在比對資料 |
| AI 適合度結果 | Must | 等級、原因、注意事項與免責清楚 |
| 報名成功 | Must | 狀態有文字與視覺改變，可回到活動 |
| 滑卡與配對成功 | Show only | 配對後可導向同一場活動 |
| Care 地圖簡卡 | Show only | 可找到電話、距離與確認時間 |
| 地點詳情／付費牆 | Show only | 免費與 locked 資訊層次看得懂 |
| Feed | Keep as is | 不造成 demo dead end 即可 |

## 5. 建議工作包（先不指定人）

三位組員可依專長認領，不建議三個人同時修改同一個主畫面。

### 工作包 A：核心流程與資訊設計

**產出**

- 地圖、活動簡卡、活動詳情、報名成功的畫面與互動。
- 三種地圖標記及底部資訊卡。
- 確保主線可從頭走到尾。

**適合的人**

- 擅長 UI flow、SwiftUI 畫面整合或 interaction 的人。

**依賴**

- 需要工作包 B 提供活動與地點資料。
- 需要工作包 C 提供 AI 結果格式。

### 工作包 B：內容、場地資料與視覺整理

**產出**

- 6 至 8 個大安區地點的 demo 資料。
- 一場主活動、兩場對照活動與參加犬資料。
- Care 地點資料、圖片選擇、規則標籤與 design system 一致性。

**適合的人**

- 擅長 UX writing、資料整理、視覺設計與 component consistency 的人。

**依賴**

- 要先沿用 PRD 中的 Nori 與主活動設定，不能各畫面使用不同版本。

### 工作包 C：AI 適合度與 demo 穩定性

**產出**

- 把 Nori、活動與場地資料送進 AI，得到固定格式的建議。
- loading、成功、失敗 fallback 三種狀態。
- 滑卡配對成功後，顯示共同適合活動的連接畫面。

**適合的人**

- 擅長 AI 串接、prompt 調整、狀態設計或 demo QA 的人。

**依賴**

- 需要工作包 B 的固定資料。
- 最後要接進工作包 A 的活動詳情，不另外做一套孤立 AI 頁面。

### Dennis：產品收斂與 demo 故事

**產出**

- 砍留裁決與文件更新。
- AI 建議文字的合理性檢查。
- 60 至 90 秒 demo 腳本與簡報說法。
- 最後一輪驗收：觀眾是否看得懂產品、AI 與線下結果。

## 6. 建議的一天節奏

| 時段 | 團隊目標 |
|---|---|
| 開始後 30 分鐘 | 三人確認主線、畫面清單、工作包 owner 與共用資料 |
| 前半段 | 各工作包完成可獨立檢查的第一版，不追求細節 |
| 中段整合 | 先接通地圖 → 活動 → AI → 報名；支線晚一點再接 |
| 後半段 | 補視覺、Care、滑卡連接與付費牆示意 |
| 最後 1 至 2 小時 | 只修 demo 會遇到的問題，跑完整腳本與備援流程 |

## 7. 完成定義（Definition of Done）

送出前，全隊一起確認：

- [ ] iPhone 上可從地圖一路完成報名，沒有 dead end。
- [ ] AI 適合度至少成功跑過一次，失敗時也有 fallback。
- [ ] AI 原因與 Nori、活動、場地資料一致，沒有亂猜。
- [ ] 同一場活動在所有畫面的名稱、時間、人數與規則一致。
- [ ] Care 清楚標示資訊確認時間，不提供醫療診斷。
- [ ] 付費牆只是示意，不會擋住緊急資訊與基本安全規則。
- [ ] 文字沒有溢出、主要按鈕可點、loading 與成功狀態看得懂。
- [ ] Demo 可在 60 至 90 秒講完，並準備網路失敗版本。
